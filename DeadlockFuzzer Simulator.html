DeadlockFuzzer simulator

Simulates the key findings of Joshi, Park, Sen and Roșu, “A Randomized Dynamic Program Analysis Technique for Detecting Real Deadlocks”, PLDI 2009, the latest of the five papers in the review.

2. Run the two passes

What the paper found, and where you can see it here

Predict, then confirm. Pass 1 watches one normal run and builds a lock-dependency graph. Any cycle in it is only a potential deadlock, so the warning can be wrong.

Zero false positives. Pass 2 re-runs the program with a scheduler that pauses threads right before the risky lock calls. A deadlock is reported only if it really happens.

Much higher hit rate. A normal scheduler rarely produces the bad interleaving. The pausing scheduler produces it almost every run (compare the bars).

Simplifications: the paper identifies a lock request by object creation context and call stack; here a request is identified by thread and line number. Pass 1 uses the paper’s cycle condition with disjoint held-lock sets (iGoodlock), limited to cycles of up to three threads.
